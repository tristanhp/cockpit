# S2 — Write-back, capture and the priority scale

Goal: Cockpit stops being read-only. You can capture, prioritise, estimate, complete and reopen work from the app, and every change goes back to its source. Product rules: [SPEC.md](../SPEC.md) (priority and effort, capture, sources). Build and verify with `npm run demo`.

## 1. Priority and effort on every task and project
- Add `priority` (0–4, Linear numbering: 0 Aucune, 1 Urgent, 2 Haute, 3 Moyenne, 4 Basse), `effort` (1/2/3/5/8 or null) and `priorityAuto` (boolean) to `tasks`. Add `priority`, `status` (`actif` | `en-attente`) and `protected` (boolean) to `projects`.
- Automatic priority, overridable. One pure function `src/engine/priority.ts` with unit tests. Rules, in order: Linear tickets use Linear's priority; a Notion row uses its `Priorité` property when the base has one; otherwise inherit the project's priority; then raise to **Urgent** when a graded deliverable or an item on a Haute project is due within 48 h.
- Project priority is derived from the existing level property while it exists: P1 → Haute, P2 → Moyenne, Maintenance → Basse, En attente → status `en-attente`, Socle → `protected` (outside the scale). The `levels` table stays for now; the UI shows priority.
- Overrides are written back when the source has the property (Linear `priority` and `estimate`; Notion `Priorité` and `Effort`), otherwise kept in a Cockpit-only `task_overrides` table that survives syncs.
- UI: Linear-style priority bars and an effort chip on task rows; both editable in the task detail panel and in the palette (`p` then a number, `e` then a Fibonacci value, when a row is focused).

## 2. Write-back
- Task: mark done and reopen, change due date, priority, effort. Notion: `pages.update` on the mapped properties (status → the first option of the "complete" group; reopen → the first "to do" option). Linear: `issueUpdate` (state of type `completed` and back to the team's first `unstarted` state, `dueDate`, `priority`, `estimate`). Read the team's workflow states once and cache them in the source's config.
- Project: edit Météo, next action, next due date, priority and status. Notion only; the Cockpit projects base is a Notion data source with known property names (see the connector's guessed mapping).
- Optimistic UI, then `refresh()`. A failed write rolls the row back and shows the error in French.
- Every write is recorded in a `change_log` table (when, entity, field, before, after, source, source response, undone flag). A "Journal des changements" section in Réglages lists the last 50 with an **Annuler** button that writes the previous value back.
- **Latest edit wins:** during a sync, if a row changed in the source after Cockpit's own write, the source value wins and the conflict is logged.
- `x` on a focused task row toggles done. The detail panel gets real controls instead of the read-only notice.

## 3. Capture and Inbox
- `c` (desktop) and a `+` tab (phone) open a one-line capture. Parse French dates (`aujourd'hui`, `demain`, weekdays, `vendredi 18h`, `12/11`) in a pure function `src/engine/capture.ts` with unit tests, and `#tags` matched with `fold()` against project names and aliases.
- Kinds: task, idea, event. When the destination is obvious (a tag, a ticket pattern, an explicit rule) file it directly; otherwise store it in an `inbox` table. Routing rules live in a `routing_rules` table (pattern → destination source and project), editable in Réglages; seed generic defaults in `src/db/demo.ts`.
- An **Inbox** view (palette entry and a link on Tâches) lists pending captures, each with a suggested destination and date. One tap files it; a "Tout ranger" button files all suggestions.
- Task creation: Notion `pages.create` in the destination data source (title, status, due, priority, effort), Linear `issueCreate` in the source's team. Ideas: write a Markdown file to `VAULT_INBOX_PATH` when that env var is set, otherwise keep them in the inbox. Events: keep them in the inbox with a note until S3 adds calendar writes.
- `POST /api/capture` with `Authorization: Bearer $COCKPIT_CAPTURE_TOKEN` accepts `{ "text": "..." }` for phone shortcuts. Return 401 without the token; document the endpoint in the README.

## 4. Linear triage
- "Pas pour moi" on an unassigned or other-assigned ticket hides it from *À trier* for good (Cockpit-only flag, stored in `task_overrides`); "Me concerne" keeps it in *Mes tâches* without reassigning in Linear.

## 5. Small things
- Dark theme only: make the dark palette the default in `globals.css` and keep the light tokens behind `[data-theme="light"]`.
- Sync every 5 minutes while a page is open, and on window focus (a small client component calling the existing sync action, with a lock so two tabs do not overlap).

## Done when
- In demo mode: a task can be captured with a date and a tag, filed, prioritised, estimated, completed and reopened; a Linear ticket can be marked "Pas pour moi"; a change can be undone from the journal; every change appears in the change log.
- `npm run check` passes. Unit tests cover the priority rules and the capture parser (at least 15 cases for dates and tags).
- The demo database fills every new table; README screenshots are not regenerated.
