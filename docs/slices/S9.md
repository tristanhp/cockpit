# S9 — Claude assists through MCP

Goal: Claude reads everything in Cockpit and proposes changes that you accept in the app. It never writes to sources directly. Depends on S2, S3 and S6. Product rules: [SPEC.md](../SPEC.md) (principles, capture, goals).

## 1. The MCP server
- Use the official `@modelcontextprotocol/sdk`. Serve it over streamable HTTP at `/api/mcp` (Next route handler that calls `connection()` first), protected by `Authorization: Bearer $COCKPIT_MCP_TOKEN` (reject with 401 otherwise; no token configured means the route returns 404). Also provide a stdio entry, `npm run mcp`, for local use with Claude Code. Demo mode serves demo data.
- `/api/mcp` is a machine endpoint: add it to `MACHINE` in `src/lib/auth/access.ts` with a test, otherwise the login gate answers MCP clients before the bearer check, and document `COCKPIT_MCP_TOKEN` in `docs/DEPLOY.md`.
- Read tools, all returning compact JSON with ids and URLs: `get_today` (day plan, blocks, urgent work), `list_tasks` (filters: status, priority, project, due before, source), `get_task`, `list_projects`, `list_goals` (with progress, signals and thread), `get_week` (blocks and budget), `search` (accent-insensitive, same as the palette), `get_habits`, `get_inbox`.
- Proposal tools (they **create a proposal row and return its id**, they do not change anything else): `propose_capture` (text, kind, destination hint), `propose_reschedule` (block id, slot), `propose_task_update` (field, value), `propose_goal_breakdown` (goal id, milestones and first tasks). Each proposal stores who and why (a short rationale from Claude).
- Tool descriptions are written for a model: say what each returns, when to use it, and that proposals need the owner's acceptance. Include the French product vocabulary in the descriptions.

## 2. Proposals inside Cockpit
- `proposals` table: id, kind, payload json, rationale, status (`pending` | `accepted` | `rejected` | `expired`), created at, decided at, result.
- A **Propositions** screen and a badge in the nav and palette. Each proposal is a card with the exact change ("Déplacer le bloc X de mar. 14:00 à mer. 09:00", "Créer la tâche …") and Accepter / Refuser. Accepting runs the same server action the UI uses (S2 write-back, S3 replan, S6 breakdown), so every guard and log applies; the change log records "via Claude".
- Pending proposals expire after seven days.
- The goal panel's **Découper avec Claude** button (S6) now shows the exact prompt to use and, when proposals exist for that goal, links to them.

## 3. Documentation
- A how-to in `docs/MCP.md`: how to add the server to Claude (claude.ai custom connector, Claude Code `claude mcp add --transport http cockpit <url> --header "Authorization: Bearer …"` and the stdio form), the tool list, an example conversation for capture, replan and goal breakdown, and the security notes (token, read-only by default, proposals only).
- `.env.example` documents `COCKPIT_MCP_TOKEN`.

## Done when
- In demo mode, driven by a small script under `scripts/` that speaks MCP to the server: list tools, call each read tool, create one of each proposal, accept one in the app's server action and see the change and its log entry; rejected and expired proposals change nothing. Unit tests cover the proposal payload validation (zod) and the bearer check.
- `npm run check` passes.
